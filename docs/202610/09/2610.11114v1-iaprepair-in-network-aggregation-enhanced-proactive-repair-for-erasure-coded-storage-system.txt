# IAPRepair: In-Network Aggregation Enhanced Proactive Repair for Erasure-Coded Storage System 

Lei Liu, Yong Wang, Junqi Chen, Member, IEEE , Yangfan Liang, Member, IEEE , Qian He, Baokang Zhao 

Abstract —Erasure-coded storage provides fault tolerance with substantially lower storage overhead than full replication, but repairing lost or at-risk blocks requires intensive cross-node data transfer. Existing reactive repair schemes start only after a failure, while proactive schemes can move data before failure but commonly treat migration, reconstruction, and network aggregation as loosely coupled operations. As a result, receiver-side bottlenecks, heterogeneous available bandwidth, and limited programmable-switch state continue to constrain repair paral-lelism. This paper presents IAPRepair, an in-network aggre-gation enhanced proactive repair framework for erasure-coded storage. IAPRepair jointly constructs each repair batch, assigns reconstruction providers and replacement nodes according to normalized transmission loads, schedules migration around the remaining receive capacity, and selectively enables in-network aggregation for reconstruction blocks that would otherwise over-load healthy nodes. The selective design reduces receiver-side traffic while retaining migration parallelism and respecting a configurable switch-resource budget. We implement IAPRepair with a Tofino programmable switch and 16 storage nodes, and evaluate it using both a prototype testbed and large-scale simu-lations. Across coding parameters, block sizes, node populations, and multiple STF-node scenarios, IAPRepair reduces repair time by at least 47.83% compared with the evaluated state-of-the-art methods. The results demonstrate that coordinating proactive repair decisions with in-network processing is an effective way to improve repair efficiency under bandwidth heterogeneity.

I. I NTRODUCTION 

Large-scale distributed storage systems increasingly rely on erasure coding to provide fault tolerance with much lower storage overhead than full replication. Reed–Solomon (RS) codes, for example, encode k data blocks into n blocks and allow a missing block to be reconstructed from any k surviving blocks. The benefit comes with a substantial repair cost: reconstructing one block requires data to be retrieved from multiple nodes, and a node failure creates many concurrent block-repair tasks. The resulting cross-node traffic prolongs the data-unavailability window and can directly affect storage-system reliability. Most existing repair systems are reactive. Pipeline-based methods such as PR, PPT, and PivotRepair reduce incast effects by coordinating transmissions across storage nodes, while RepairBoost and SelectiveEC balance repair workloads after a failure has occurred [1]–[5]. Failure prediction makes it possible to repair data before a node becomes unavailable. We refer to a node predicted to fail as a soon-to-fail (STF) node. Proactive repair can either migrate STF blocks directly to healthy nodes or reconstruct them from surviving blocks, and recent systems such as FastPR and LFPR combine these two operations in batches [6]–[12]. Nevertheless, current proac-tive schemes do not sufficiently coordinate receiver capacity, bandwidth heterogeneity, and the choice between migration and reconstruction. The central difficulty is an asymmetric traffic pattern. Both STF and healthy nodes may provide repair data, but only healthy nodes can receive repaired blocks. Concurrent mi-gration and reconstruction can therefore overload a small subset of healthy receivers. The problem is amplified when the available bandwidth of storage nodes is shared with front-end workloads and differs across nodes. A repair schedule that is balanced in terms of block counts can still be highly imbalanced in transmission time. Programmable switches provide a complementary opportu-nity. In-network aggregation (INA) can combine reconstruc-tion traffic on the forwarding path and reduce the volume delivered to storage nodes. Existing INA-based repair systems, including NetEC, Paint, and InaPR, primarily target reactive repair [13]–[15]. Applying INA to proactive repair, however, raises two coupled questions: which reconstruction blocks should consume scarce switch state, and how should migration and reconstruction tasks be assigned when node bandwidth is heterogeneous? B. Proactive repair 

Proactive repair, based on failure prediction, repairs the blocks stored on STF nodes. Compared to reactive repair, proactive repair exhibits two advantages. (1) Conducting data repair prior to failure occurrence achieves consistent data availability and enhances the reliability of the storage system. (2) Repair can be performed simultaneously via both migration and reconstruction, achieving higher repair efficiency. As illustrated in Fig. 3, the number of healthy nodes is typically much larger than that of STF nodes. Migration (the green line) directly copies a block from the STF node to the replacement node, which incurs a low data transmission overhead. How-ever, since only the STF node can supply data for migration, the repair parallelism is inherently limited. Reconstruction (the blue lines) retrieves blocks from multiple healthy nodes. Although reconstruction enables parallel repair of multiple blocks, it requires a larger volume of data to reconstruct a single block. C. In-network aggregation 

In-network aggregation is a technique that offloads data aggregation tasks (e.g., summation, averaging, counting, etc.) from severs to network devices. Aggregating the repair traffic directly on network devices along the transfer paths can reduce network load and alleviate bandwidth bottlenecks. Unlike traditional fixed-function switches, the Intel Tofino programmable switch [19] enables users to execute custom computation, storage and logical processing operations during packet forwarding via the P4 programming language [20]. The arithmetic logic units and SRAM-based stateful objects (e.g., registers) within the programmable switch can be uti-lized to implement data aggregation. Since erasure-coded data repair requires aggregating data from multiple nodes, the programmable switch can be leveraged to enhance the data reconstruction efficiency. However, in-network aggregation with programmable switches faces challenges such as scarcity of switch internal resources and the impact of uncertainty in packet arrival time on aggregation performance [13], [14]. 

D. Related work 

Existing repair techniques can be organized along two di-mensions: whether repair is triggered after a failure or before a predicted failure, and whether computation remains on storage nodes or is partially offloaded to network hardware. Table I summarizes the distinctions most relevant to IAPRepair. Reactive repair methods operate after a failure has been observed. PR partitions repair traffic into a pipeline, whereas PPT and PivotRepair refine the pipeline structure to reduce incast and improve transmission overlap [1]–[3]. RepairBoost, SelectiveEC, SMFRepair, and SARepair further address work-load placement or repair-stripe selection to balance node-side traffic [4], [5], [21], [22]. These methods improve reactive repair efficiency, but they do not exploit the additional time available before a predicted failure. Proactive repair methods use failure prediction to move data before a node becomes unavailable. Proactive Replication and ProCode reduce the risk of a future failure through migration or replication, at the cost of additional traffic or storage overhead [23], [24]. FastPR couples migration with reconstruction in a batched workflow, and LFPR extends the idea with a lazy strategy for mobile distributed storage [11], [12]. These approaches establish the basis for IAPRepair, but their scheduling decisions do not jointly account for receiver-side contention, heterogeneous available bandwidth, and limited in-network state. Programmable-network repair methods move part of the re-pair computation into the network. NetEC and INC-EC offload decoding or decoding-related operations to programmable switches, while AggreTree, XORInc, Paint, and InaPR use host–switch collaboration to aggregate repair traffic [13]–[15], [25]–[27]. SmartNIC- and accelerator-based designs provide another hardware-assisted direction [28], [29]. These methods reduce data movement, but they primarily target reactive repair and do not solve the joint scheduling problem of proactive migration and reconstruction. IAPRepair fills this gap by cou-pling load-aware proactive batch construction with selective INA under an explicit switch budget. III. SYSTEM ARCHITECTURE AND PROBLEM FORMULATION

IAPRepair is a proactive repair framework for erasure-coded data built on programmable networks. It enhances the parallelism of migration and reconstruction. Specifically, IAPRepair selects STF blocks to be reconstructed for each batch based on the available bandwidth of each node, and assigns reconstruction tasks to individual nodes. Subsequently, based on the reconstruction load of each node, it selects an appropriate number of STF blocks for migration and assigns a replacement node for each migrated STF block. Finally, IAPRepair determines which STF blocks should be reconstructed using in-network aggregation. 

A. Block selection for reconstruction 

Leveraging in-network aggregation can substantially reduce the bandwidth demand of data reconstruction, which elimi-nates the bandwidth contention between migration and recon-struction. Consequently, migration and reconstruction can be considered separately. IAPRepair first selects STF blocks to be reconstructed for a batch solely from the perspective of maximizing reconstruction efficiency. As illustrated by the blue lines in Fig. 3, since in-network aggregation reduces the volume of data received by nodes during reconstruction, the uplink bandwidth is more likely to become the bottleneck limiting reconstruction efficiency. IAPRepair prioritizes the utilization of the uplink bandwidth of healthy nodes. For any two nodes hi and hj , if nui /u i < n uj /u j , hi is rel-atively more idle than hj . When adding reconstruction blocks to a batch, priority should be given to assigning reconstruction tasks to idle nodes, so as to improve the utilization of their uplink bandwidth. data blocks are partitioned into k/r groups ( k is divisible by r

). Each group contains r data blocks and one local parity block. The local parity block is generated from the data blocks within the same group. In addition, LRC (n, k, r ) contains n−k−k/r

STF nodes store both global parity blocks and local blocks, and the number of global parity blocks is smaller. Since the data volume required to reconstruct a local block is substantially less than that required for a global parity block, IAPRepair prioritizes repairing global parity blocks through migration. In the prototype system, the programmable switch is em-ployed for data forwarding and in-network aggregation, as illustrated in Fig. 8. The programmable switch comprises the Parser, the Forward module, and multiple aggregators. The Parser identifies whether a packet requires in-network aggregation based on its Type field. Reconstruction packets carrying specific markings are distributed to the aggregator group, while all other packets (including both reconstruction and migration packets) are directly dispatched to the Forward module. The Aggregator serves as the core component for in-network aggregation, and perform aggregation operations on the marked reconstruction packets. The aggregated results are subsequently delivered to the Forward module. In the figure, blue lines represent reconstruction data flows, and green lines represent migration data flows. Only a portion of the reconstruction data requires in-network aggregation. STF nodes transmit migration data, and do not receive any repair data. Healthy nodes transmit reconstruction data and receive both migration and reconstruction data. IAPRepair allocates a group of aggregators to each STF block reconstructed via in-network aggregation. This design enables nodes to transmit data continuously without await-ing receiver acknowledgments, thereby preventing throughput degradation caused by acknowledgment waiting. Assuming that each group contains Na aggregators, the sender can trans-mit at least Na packets consecutively. Additionally, multiple aggregators function as data buffers, mitigating the impact of differences in packet arrival times from different nodes on aggregation efficiency. Each aggregator maintains three state objects: rCnt, rVer, and rData. Aggregators within the same group share a common rNum state object. All of these state objects are implemented using Register objects in the programmable switch. The rNum register stores the number of data flows required for aggre-gation and is configured before proactive repair begins. The rData register stores the intermediate aggregation result. Upon receiving a packet, the aggregator performs a bitwise XOR 10 

operation between rData and the packet’s Data field, writes the result back to rData, and increments rCnt. When the value of rCnt equals to that of rNum, indicating that all aggregation operations required for decoding have been completed, the aggregator dispatches the data stored in rData to the Forward module and resets rData. The Pid and Bid fields are used to identify the aggre-gator group and the specific aggregator within that group, respectively. Packets for repairing the same STF block carry an identical Pid. The Seq field indicates the offset of the carried data within the STF block and is employed to handle out-of-order packet arrivals. Due to the limited resources of programmable switches, a single aggregator is shared by packets with different Seq, with Bid cycling repeatedly from 1 to Na. However, aggregator sharing may lead to aggre-gation of packets with differing Seq. To prevent this, the sender increments the Ver field by 1 after every Na packets transmitted. Correspondingly, rVer is incremented by 1 upon completing aggregation of rNum packets. If the value of Ver differs from that of rVer, a transmission error is detected, and the corresponding data must be retransmitted. VI. E VALUATION

The proposed IAPRepair performs proactive repair on the STF node based on accurate node failure prediction. We first analyze the factors influencing proactive repair.
